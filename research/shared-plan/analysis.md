# THE ROOT 기획 검토 — 공개 본문 기반 예비 분석

> 원본 제공 후 검토한 [original_review.md](original_review.md)가 이 예비 분석을 대체한다. 아래 미확정 항목 중 OBSERVE/SKIP 비용, HOLD 점유·유지, Refresh 제한 등은 원본에서 해결됐다.

## 판단

분류 판단과 성장·상점 선택을 연결하려는 게임으로 읽힌다. 이는 공개된 시스템 이름에서 도출한 해석이다. 정확한 승리·패배 조건과 한 판의 흐름은 원본 기획안이 없어 확정할 수 없다.

상점 규칙은 상당히 구체적이다. 그러나 공개 본문만으로는 핵심 분류 플레이가 재미있는지, 경제가 성립하는지, 구현 명세가 완결됐는지 판단할 수 없다. 기존 대화의 “바로 개발 가능한 상태”라는 평가는 원본과 플레이 검증을 거쳐야 한다.

## 장점

1. 확정 규칙과 밸런스 가안을 나눈 방식이 좋다. 수치를 조정할 때 게임의 기본 약속까지 흔들릴 가능성을 줄인다.
2. 첫 상점 강화품 보장은 강화 시스템을 직접 보여줄 기회를 제공한다. 단, 구매할 재화와 설명이 있어야 실제 학습으로 이어진다.
3. HOLD와 유료 갱신은 지금 구매할지, 재화를 모을지, 다른 재고를 찾을지 선택하게 한다.
4. 강화 실패가 없다는 규칙은 손실 운보다 자원 배분에 집중하게 한다.
5. 고양이·물·오리너구리 3개체로 시작하는 제안은 작은 범위에서 분류 규칙의 명료성을 검증하기에 적합하다.

## 먼저 검증할 문제

### 1. 분류가 추론인가, 정답 암기인가

30개체를 반복 제시하면 정답 경로를 외우는 문제가 생길 수 있다. 다만 실제 데이터와 출제 방식은 보지 못했으므로 결함으로 단정할 수 없다. 새 개체에도 관찰 단서와 분류 원리를 적용할 수 있는지 확인해야 한다. Distractor는 그럴듯하되 오답 이유를 설명할 수 있어야 한다.

### 2. Observe/Lock/Skip이 실제 선택이 되는가

Observe의 비용·정보량, Lock의 성공·실패 결과, Skip의 불이익이 공개 본문에 없다. Observe가 무료이며 무제한이면 항상 관찰하는 행동이 우세할 수 있고, Skip이 너무 유리하면 어려운 카드 회피가 정답이 될 수 있다. 세 행동의 비용과 상태 변화를 먼저 명시해야 한다.

### 3. 상점 확률의 적용 대상

강화 단계 확률은 합계 100%다. 그러나 5칸에는 재료도 들어가는 예시가 있어, 이 확률을 장비가 선택된 뒤 적용하는지 전체 슬롯에 적용하는지 분명하지 않다. 장비/재료 추첨 → 품목 추첨 → 장비 강화 단계 추첨 순서인지 원문 확인이 필요하다.

### 4. HOLD와 보장 규칙의 경계

HOLD가 5칸 중 하나인지 별도 슬롯인지, 수동 갱신에도 유지되는지, 첫 상점 보장이 최초 진열만인지 갱신마다 적용되는지 확인해야 한다. 가격과 강화 단계도 함께 고정되는지, 저장·불러오기 이후 유지되는지도 필요하다.

### 5. 새로고침 수열의 끝

50 → 100 → 200 → 400 이후 비용 또는 횟수 제한은 공개 본문에 없다. 네 번의 누적 비용은 750이다. Cycle 수입이 없어 부담의 적정성은 평가할 수 없다. 다섯 번째 동작의 처리와 UI 설명이 필요하다.

### 6. 직접 강화와 완제품 구매의 비교 기준

15~30% 프리미엄의 기준이 기본 장비값, 강화 수수료, 재료의 상점가·기회비용 중 무엇을 포함하는지 정해야 한다. 이를 정의하지 않으면 재료 단가만 바꿔도 구매와 강화의 우열이 크게 달라질 수 있다. Mastery 0 규칙과 기존 장비 숙련도 유지 방식도 함께 검토해야 한다.

### 7. MVP 범위

Depth, Overflow, Hard Mode, 숙련도 진화, 강화, 상점을 한꺼번에 넣으면 핵심 분류 조작의 문제와 성장 시스템의 문제를 분리하기 어렵다. 우선 3개체 분류 → 결과 피드백 → Cycle 완료까지 만든 뒤 상점과 장비 1종을 연결하는 순서를 제안한다. 이는 새 제안이며 기존 확정안을 변경한 것이 아니다.

## 데이터와 구현 검토 항목

원본 확보 후 아래를 확인한다.

- Excel과 JSON 중 편집 원본을 하나로 지정하고 다른 쪽을 자동 생성하는가.
- 개체·분류 노드·아이템 ID가 유일하며 참조 누락과 트리 순환을 검출하는가.
- Canon Path와 Distractor가 논리적으로 모순되지 않는가.
- 상점 보장·HOLD·확률이 충돌하지 않는가.
- 저장 데이터와 정적 콘텐츠 데이터가 구분되는가.
- 난수 seed와 상점 상태를 저장해 불러오기 때 임의 재추첨이 발생하지 않는가.
- 점수·재화·숙련도 변경이 화면 코드와 분리돼 있는가.
- 규칙 버전 및 저장 형식 버전이 있는가.

프로토타입에서 SQLite가 반드시 필요한지는 데이터 조회·저장 요구를 보고 결정한다. JSON과 SQLite를 둘 다 쓴다는 사실만으로 구조가 좋아지는 것은 아니다.

## 첫 플레이 검증 제안

1. 고양이·물·오리너구리의 분류 경로와 단서, 오답 설명을 수작업 검토한다.
2. Observe/Lock/Skip을 실행하고 결과와 비용을 즉시 이해할 수 있는 3장짜리 플레이를 만든다.
3. 판단 시간, 관찰 횟수, 오답·건너뛰기 비율, 반복 플레이 때의 변화량을 기록한다.
4. Cycle 완료 후 장비 1종·재료·HOLD·갱신을 연결한다.
5. 구매 대 직접 강화 선택, Cycle당 순수입, 목표 장비 도달 시간을 비교한다.
6. 핵심 플레이의 이해 가능성과 반복 재미를 확인한 후 30개체와 추가 난도로 확장한다.

정량 합격선은 목표 세션 길이, 타깃 플레이어, 실제 테스트 결과가 없으므로 임의로 확정하지 않는다.

## 남은 제약

원본 다운로드는 완료되지 않았다. Excel/JSON 일치 여부, 30개체의 정답, SQL 구조, 네 MD 간 모순, 이미지 방향성은 아직 검토하지 못했다. 가장 먼저 필요한 자료는 THE_ROOT_Vertical_Slice_DevPack_v0.3.zip 원본이다.
